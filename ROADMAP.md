# План дальнейшей разработки

Состояние на момент фиксации: фазы 0-5 закрыты (конфиг + мультивендорный GPU,
обработка ошибок, автотесты + CI, общий backend `Assistant`, три интерфейса
TUI/GUI/консоль, barge-in, упаковка в pip-пакет). 64 автотеста, чистый ruff.

Главная цель следующего этапа — **live talk**: разговор без ощутимых пауз,
а не «нажал, подождал, услышал». Всё остальное подчинено ей.

---

## 0. Бюджет задержки — что реально мешает live talk

Полный цикл реплики складывается из:

```
[запись] -> STT -> LLM (до первого токена) -> TTS (первая фраза) -> звук
```

Измеренное на стенде (AMD RX 9060 XT, ROCm), после прогрева моделей,
на тестовом аудио 9.61с:

| Этап | Где считается | Время | RTF |
|---|---|---|---|
| **STT, whisper `medium` int8** | **CPU** | **5.86с** | **0.61x** |
| TTS, `nfe_step=32` (дефолт) | GPU (ROCm) | ~1.7с на фразу | — |
| TTS, `nfe_step=16` | GPU (ROCm) | ~0.9с | — |
| TTS, `nfe_step=8` | GPU (ROCm) | ~0.45с | — |
| LLM (gpt-oss:20b, до первого токена) | GPU (Ollama) | не замерялось | — |

Разовые издержки старта (в бюджет реплики не входят, но влияют на время
запуска приложения): загрузка whisper `medium` ~3.1с, первый вызов F5-TTS
~7с (компиляция GPU-ядер).

**Вывод замера: узкое место — STT, а не TTS.** Распознавание на CPU
занимает в 3.4 раза больше времени, чем синтез на GPU. При RTF 0.61x даже
короткая команда в 3 секунды речи стоит ~1.8с распознавания; вместе с LLM и
TTS (~1.7с) полный цикл уверенно превышает 4 секунды. Для ощущения живого
разговора нужен отклик меньше секунды — то есть **STT обязан переехать на
GPU**, иначе никакая оптимизация TTS погоды не сделает.

Замеры `small`/`base` не сняты (модели не скачаны) — сделать вместе с
задачей 1c. Черновой скрипт бенчмарка лежал в scratchpad; его нужно оформить
как `scripts/bench_pipeline.py`, чтобы замер воспроизводился и на
NVIDIA-машине (и включал LLM time-to-first-token).

## 1. STT на GPU — главный блокер (приоритет 1)

Сейчас в [stt_engine.py](stt_engine.py) захардкожено `device="cpu"`. Это не
случайность и не лень: **CTranslate2 (движок faster-whisper) поддерживает
только CUDA и CPU, ROCm им не поддерживается**. То есть на NVIDIA проблема
решается одной строкой, а на AMD — нет.

### 1a. NVIDIA — дешёвая победа
Выбирать устройство по `gpu.detect_backend()`: при `cuda` передавать
`device="cuda"`, `compute_type="float16"`. Ожидаемо кратное ускорение STT.
Это надо было сделать ещё в фазе 0 (тогда мультивендорность довели только
до TTS) — долг.

### 1b. AMD — нужен другой движок STT
Варианты, в порядке предпочтения:

1. **Whisper через уже установленный ROCm-torch.** Самый прямой путь: torch
   на этой машине уже собран под ROCm и работает (F5-TTS на нём и крутится).
   Значит `transformers`-реализация Whisper (или референсный `openai-whisper`)
   пойдёт на GPU без нового рантайма. Медленнее CTranslate2 по архитектуре,
   но GPU против CPU почти наверняка перевесит. **Проверить первым.**
2. **whisper.cpp с Vulkan-бэкендом.** Vulkan работает на AMD; есть Python-
   биндинги (`pywhispercpp`). Плюс — очень лёгкий рантайм, минус — ещё одна
   нативная зависимость в сборке.
3. **ONNX Runtime + DirectML.** На Windows работает поверх любой GPU,
   включая AMD. Минус — конвертация модели в ONNX и лишний тяжёлый рантайм.

Архитектурно: ввести в `stt_engine.py` абстракцию бэкенда по аналогии с
[gpu.py](gpu.py), чтобы движок выбирался под железо, а `Assistant` про это
не знал. Тесты уже мокают `WhisperModel` — менять их не придётся.

### 1c. Модель поменьше
`medium` для команд типа «открой калькулятор» избыточен. Замерить `small` и
`base`: если качество распознавания русского остаётся приемлемым, это
ускорение без всякой смены рантайма. Вынести размер в конфиг (уже вынесен,
`stt.model_size`) и подобрать дефолт по замерам.

## 2. События вместо print — интерфейсы должны «говорить» (приоритет 1)

Сейчас [assistant.py](assistant.py) на любую проблему делает `print()`:
«не удалось связаться с Ollama», «обрыв потока», `[TTS error]`. В консоли это
видно, но **в TUI Textual перехватывает экран, а в GUI вывод уходит в никуда** —
пользователь просто получает пустой ответ и не понимает почему.

Плюс к этому: ответ приходит в UI одним куском. Токены уже стримятся в TTS
(`StreamingSpeaker`), но текст на экране появляется только когда модель
договорила — голос уже звучит, а экран пуст.

Обе задачи решаются одним изменением: `Assistant` перестаёт печатать и
начинает отдавать события наружу (колбэки `on_token`/`on_error`/`on_tool_call`
или очередь событий). Каждый интерфейс рендерит их по-своему: консоль —
`print`, TUI — в `RichLog`, GUI — в транскрипт. Это разблокирует и стриминг
текста, и нормальные сообщения об ошибках.

## 3. Прерываемый TTS — barge-in до конца (приоритет 2)

`TTSEngine.interrupt()` выбрасывает очередь и глушит воспроизведение, но
фразу, которую воркер уже начал синтезировать, прервать нельзя: `tts.infer()`
не поддерживает отмену. На практике — перебил ассистента, а он ещё секунду-две
договаривает. Нужно вынести синтез в отменяемую задачу (проверка флага между
шагами диффузии либо синтез чанками поменьше).

## 4. Таймауты и живучесть (приоритет 2)

- Нет таймаутов на запросы к Ollama: если сервис завис (не упал, а именно
  завис) — интерфейс ждёт бесконечно, без индикации.
- Нет проверки при старте, что Ollama вообще запущен и нужная модель есть.
- `switch_model()` не проверяет существование модели — ошибка вылезет только
  при следующем запросе.
- `available_models` статичен в конфиге, хотя `ollama.list()` даёт реальный
  список установленных.

---

## 5. Память диалога (приоритет 2)

`Assistant.messages` растёт без ограничений и не сохраняется между запусками:
через час разговора контекст распухнет и модель начнёт тормозить, а после
перезапуска — полная амнезия. Нужен триминг по токенам (со сохранением
system-промпта) и персистентность истории на диск.

---

## 6. Безопасность: белый список расширений (приоритет 2)

`open_file` открывает файл через `os.startfile`, а `files.root_dir` по
умолчанию `"."` — корень проекта. Path traversal закрыт и покрыт тестами, но
`.exe`/`.bat`/`.ps1` внутри разрешённой директории откроются, то есть
выполнятся. Сейчас граница проведена по пути, а правильнее ещё и по типу
файла — добавить `files.allowed_extensions`.

## 7. Функциональность (приоритет 3)

- **Добавление голоса из интерфейса.** [scripts/transcribe_ref.py](scripts/transcribe_ref.py)
  умеет транскрибировать референс, но никуда не подключён. Сценарий «записать
  10 секунд с микрофона → получить новый голосовой профиль» напрашивается,
  тем более что дизайн-макет это предполагал.
- **VAD / wake word.** Сейчас только push-to-talk (клавиша/клик). Для
  «Jarvis-образа» это главное недостающее звено и самое дорогое в реализации.
  Разумный промежуточный шаг — VAD для автоматического определения конца
  фразы (тогда не нужно жать второй раз), wake word — потом.
- **Язык распознавания зашит как `ru`** — вынести в конфиг.

## 8. Инфраструктура (приоритет 3)

- CI гоняется только на Windows и ставит CPU-torch. Стоит добавить Linux-job

## Рекомендуемый порядок

1. **STT на GPU** (задача 1) — замером подтверждено, что это главный блокер
   live talk. Для NVIDIA — одна строка, для AMD — сначала проверить Whisper
   поверх уже работающего ROCm-torch.
2. **События вместо print + стриминг текста** (задача 2) — самый заметный
   эффект для UX, разблокирует нормальные ошибки в интерфейсах.
3. Оформить `scripts/bench_pipeline.py` и добрать недостающие замеры
   (`small`/`base`, LLM time-to-first-token) — чтобы прогресс по задаче 1
   можно было измерять, а не оценивать на глаз.
4. Дальше по приоритетам: прерываемый TTS, таймауты, память диалога.
