## 0. Бюджет задержки — что реально мешает live talk

Полный цикл реплики складывается из:

```
[запись] -> STT -> LLM (до первого токена) -> TTS (первая фраза) -> звук
```

Измеренное на стенде (AMD RX 9060 XT, ROCm), после прогрева моделей,
на тестовом аудио 9.61с:

| Этап | Где считается | Время | RTF |
|---|---|---|---|
| **STT, whisper `medium` int8** | **CPU** | **5.86с** | **0.61x** |
| TTS, `nfe_step=32` (дефолт) | GPU (ROCm) | ~1.7с на фразу | — |
| TTS, `nfe_step=16` | GPU (ROCm) | ~0.9с | — |
| TTS, `nfe_step=8` | GPU (ROCm) | ~0.45с | — |
| LLM (gpt-oss:20b, до первого токена) | GPU (Ollama) | не замерялось | — |

Разовые издержки старта (в бюджет реплики не входят, но влияют на время
запуска приложения): загрузка whisper `medium` ~3.1с, первый вызов F5-TTS
~7с (компиляция GPU-ядер).

**Первоначальная гипотеза (по `medium`):** узкое место — STT на CPU, оно
обязано переехать на GPU, иначе отклик меньше секунды недостижим.

### Замер опроверг гипотезу — `scripts/bench_pipeline.py`, 2026-08-28

Оформлен воспроизводимый бенчмарк (`gogi-bench`). Прогон на том же стенде
(AMD RX 9060 XT, ROCm), то же аудио 9.61с, медиана из 3 замеров:

| Ступень | Устройство | Время | RTF | CER |
|---|---|---|---|---|
| STT `base` int8 | CPU | **0.51с** | 0.05x | 3.2% |
| STT `small` int8 | CPU | **1.79с** | 0.19x | 1.1% |
| STT `medium` int8 | CPU | 5.79с | 0.60x | 0.0% |
| LLM gpt-oss:20b, TTFT (тёплая) | GPU | 0.8–3.5с | — | — |
| LLM gpt-oss:20b, TTFT (первый вызов) | GPU | ~7с | — | — |
| TTS `nfe_step=8` | GPU | 0.40с | — | — |
| TTS `nfe_step=16` | GPU | 0.76с | — | — |
| TTS `nfe_step=32` | GPU | 1.52с | — | — |

**Новый вывод:** STT на GPU НЕ нужен для цели «STT < 1 с». Модель `base` на
CPU распознаёт весь клип 9.6с за полсекунды при CER 3.2% на живой русской
речи (для коротких команд ошибок практически не будет); `small` — 1.8с при
CER 1.1%. Достаточно **сменить дефолт `stt.model_size` на `base` или
`small`** и подрезать вход VAD-эндпоинтингом. Задача 1 (STT на GPU)
понижается в приоритете: NVIDIA-строчка (1a) остаётся как дешёвый долг,
абстракция бэкендов под AMD (1b) — откладывается до появления реальной
потребности.

**Куда переехало узкое место:** теперь доминирует и сильнее всего скачет
**LLM time-to-first-token** (0.8–3.5с у gpt-oss:20b, а на пути с tool-call —
до ~2–3с молчания перед голосом). Отсюда приоритеты смещаются на:
агрессивную нарезку первой фразы в синтез («Секунду…» уходит в TTS сразу),
события/стриминг текста в UI, и — отдельной задачей — оценку меньшей LLM
или отключения reasoning.

Свежие JSON-отчёты бенчмарка — в `benchmarks/` (в .gitignore), зафиксирован
`benchmarks/baseline.json`.

## 1. STT на GPU — ~~главный блокер~~ понижено (было: приоритет 1)

> **Статус (28.08.2026, ветка `v0.2-live-core`).** Замер (раздел 0) снял
> этот пункт с приоритета. `small` на CPU — 1.8с / CER 1.1% на клипе 9.6с
> (на реальной команде 2-3с — доли секунды), `base` — 0.5с. Цель «STT < 1с»
> достигается сменой модели, без GPU. Дефолт `stt.model_size` уже `small`
> (задача 1c закрыта). Осталось из этого раздела:
> - **1a (NVIDIA)** — по-прежнему стоит сделать как дешёвый долг: одна ветка
>   в `stt_engine.py` по `gpu.detect_backend()`.
> - **1b (AMD-движок)** — заморожено. Разморозить только если появится
>   потребность в `medium`/`large` на скорости (напр. многоязычие,
>   диктовка), которую CPU не тянет.

Сейчас в [stt_engine.py](stt_engine.py) захардкожено `device="cpu"`. Это не
случайность и не лень: **CTranslate2 (движок faster-whisper) поддерживает
только CUDA и CPU, ROCm им не поддерживается**. То есть на NVIDIA проблема
решается одной строкой, а на AMD — нет.

### 1a. NVIDIA — дешёвая победа
Выбирать устройство по `gpu.detect_backend()`: при `cuda` передавать
`device="cuda"`, `compute_type="float16"`. Ожидаемо кратное ускорение STT.
Это надо было сделать ещё в фазе 0 (тогда мультивендорность довели только
до TTS) — долг.

### 1b. AMD — нужен другой движок STT
Варианты, в порядке предпочтения:

1. **Whisper через уже установленный ROCm-torch.** Самый прямой путь: torch
   на этой машине уже собран под ROCm и работает (F5-TTS на нём и крутится).
   Значит `transformers`-реализация Whisper (или референсный `openai-whisper`)
   пойдёт на GPU без нового рантайма. Медленнее CTranslate2 по архитектуре,
   но GPU против CPU почти наверняка перевесит. **Проверить первым.**
2. **whisper.cpp с Vulkan-бэкендом.** Vulkan работает на AMD; есть Python-
   биндинги (`pywhispercpp`). Плюс — очень лёгкий рантайм, минус — ещё одна
   нативная зависимость в сборке.
3. **ONNX Runtime + DirectML.** На Windows работает поверх любой GPU,
   включая AMD. Минус — конвертация модели в ONNX и лишний тяжёлый рантайм.

Архитектурно: ввести в `stt_engine.py` абстракцию бэкенда по аналогии с
[gpu.py](gpu.py), чтобы движок выбирался под железо, а `Assistant` про это
не знал. Тесты уже мокают `WhisperModel` — менять их не придётся.

### 1c. Модель поменьше — СДЕЛАНО (28.08.2026)
Замерены `small`/`base` (раздел 0). Дефолт `stt.model_size` переведён
`medium -> small` в `config.example.yaml` с комментарием про компромиссы.
`base` — вариант для максимальной отзывчивости на простых командах.

## 2. События вместо print — СДЕЛАНО (28.08.2026, ветка `v0.2-live-core`)

Было: [assistant.py](assistant.py) на любую проблему делал `print()` —
в TUI Textual перехватывает экран, в GUI вывод уходил в никуда; ответ
приходил в UI одним куском уже после того, как голос отзвучал.

Реализовано:

- **[events.py](events.py)** — `EventEmitter` + `Event` (`STATE_CHANGED`,
  `LLM_TOKEN`, `LLM_DONE`, `TOOL_STARTED/DONE`, `TTS_STARTED/DONE`,
  `STT_DONE`, `INTERRUPTED`, `ERROR`). Колбэки, не очередь: у потребителей
  уже есть свой маршалинг в UI-поток. Сломанный слушатель не роняет ядро.
- **[state.py](state.py)** — явная машина состояний
  `IDLE → LISTENING → TRANSCRIBING → THINKING → [EXECUTING_TOOL] → SPEAKING
  → IDLE`, плюс `ERROR` и barge-in из любого состояния. Нелегальный
  переход → `InvalidTransition`. (Пункт из внешнего аудита, не было в
  исходном роадмапе.)
- **`Assistant`** наследует `EventEmitter`, держит `StateMachine`, эмитит
  события по всему ходу диалога. Публичный API не изменился. Новый метод
  `interrupt()` (barge-in + сброс `StreamingSpeaker` + переход состояния).
- **[main.py](main.py)** подписан: печатает поток токенов, вызовы
  инструментов, ошибки.
- **[tui.py](tui.py)** — стриминг ответа по токенам в виджет `#streaming`,
  индикатор состояния в подзаголовке, ошибки и tool-вызовы в транскрипт.
- **[tts_engine.py](tts_engine.py)** `StreamingSpeaker` — первый кусок
  ответа режется по раннему рубежу (запятая/двоеточие/тире или предел
  60 симв.), дальше по предложениям. Первая фраза уходит в синтез, не
  дожидаясь точки — бьёт по доминирующей теперь задержке LLM TTFT.

Осталось: подписать **GUI** ([gui.py](gui.py) / `gui/index.html`) на те же
события — сейчас он ещё работает по-старому.

## 3. Прерываемый TTS — barge-in до конца (приоритет 2)

`TTSEngine.interrupt()` выбрасывает очередь и глушит воспроизведение, но
фразу, которую воркер уже начал синтезировать, прервать нельзя: `tts.infer()`
не поддерживает отмену. На практике — перебил ассистента, а он ещё секунду-две
договаривает.

Замер (раздел 0) снизил остроту: при `nfe_step=8` синтез фразы — 0.40с, то
есть worst-case «доигрывания» ~полсекунды одной фразы. Ранняя нарезка
(`StreamingSpeaker`, задача 2) уже дробит ответ на мелкие куски. Достаточный
следующий шаг — резать ещё мельче и на `interrupt()` дропать текущий буфер;
**лезть внутрь диффузии F5-TTS не нужно** (низкий ROI, подтверждено внешним
аудитом).

## 3b. LLM time-to-first-token — новый доминирующий член задержки

Замер: gpt-oss:20b даёт TTFT 0.8–3.5с (сильно скачет — reasoning-модель), на
пути с tool-call — ~2–3с молчания перед голосом. Это теперь главный вклад в
TTFA. Что пробовать:

- прогрев модели при старте (первый вызов ~7с против ~1с на тёплой);
- `think=False` / не-reasoning модель для команд, либо более мелкая модель
  (gpt-oss меньше, qwen и т.п.) — замерить через `gogi-bench`;
- филлер-фраза («Секунду…») в синтез сразу по факту `LLM_STARTED`, не
  дожидаясь первого токена — закрывает паузу на tool-пути.

## 4. Таймауты и живучесть (приоритет 2)

- Нет таймаутов на запросы к Ollama: если сервис завис (не упал, а именно
  завис) — интерфейс ждёт бесконечно, без индикации.
- Нет проверки при старте, что Ollama вообще запущен и нужная модель есть.
- `switch_model()` не проверяет существование модели — ошибка вылезет только
  при следующем запросе.
- `available_models` статичен в конфиге, хотя `ollama.list()` даёт реальный
  список установленных.

## 5. Память диалога (приоритет 2)

`Assistant.messages` растёт без ограничений и не сохраняется между запусками:
через час разговора контекст распухнет и модель начнёт тормозить, а после
перезапуска — полная амнезия. Нужен триминг по токенам (со сохранением
system-промпта) и персистентность истории на диск.

---

## 6. Безопасность: белый список расширений (приоритет 2)

`open_file` открывает файл через `os.startfile`, а `files.root_dir` по
умолчанию `"."` — корень проекта. Path traversal закрыт и покрыт тестами, но
`.exe`/`.bat`/`.ps1` внутри разрешённой директории откроются, то есть
выполнятся. Сейчас граница проведена по пути, а правильнее ещё и по типу
файла — добавить `files.allowed_extensions`.

## 7. Функциональность (приоритет 3)

- **Добавление голоса из интерфейса.** [scripts/transcribe_ref.py](scripts/transcribe_ref.py)
  умеет транскрибировать референс, но никуда не подключён. Сценарий «записать
  10 секунд с микрофона → получить новый голосовой профиль» напрашивается,
  тем более что дизайн-макет это предполагал.
- **VAD / wake word.** Сейчас только push-to-talk (клавиша/клик). Для
  «Jarvis-образа» это главное недостающее звено и самое дорогое в реализации.
  Разумный промежуточный шаг — VAD для автоматического определения конца
  фразы (тогда не нужно жать второй раз), wake word — потом.
- **Язык распознавания зашит как `ru`** — вынести в конфиг.
